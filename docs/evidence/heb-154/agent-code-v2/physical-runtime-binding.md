## 3. PB-runtime — topology and access

The trust-boundary model and transport-only provider relay are accepted. PB-transport also accepts the separate private administration socket model below. Exact network names, socket ownership/commands, launch settings and other physical bindings remain proposed or pending; runtime access enforcement and the separate builder-isolation gate are unproved.

### Trust and supplied components

The trusted computing base is the operator/custodian, host OS, container engine, supplied fixture, its PostgreSQL service/administrators and evidence collector. The boundary protects hidden material and service state from the cold builder and built application. It is not a claim of protection against a hostile host/database administrator or an unknown container escape. Such a threat would reopen the runtime choice.

Docker's documented namespace and capability mechanisms support the proposal, but its security documentation also identifies daemon access and overly broad mounts as risks. Consequently, enforcement must be inspected and exercised rather than inferred from a container name. [Docker Engine security](https://docs.docker.com/engine/security/)

| Runtime actor | Supplied access and durable state | Excluded access |
|---|---|---|
| Host supervisor/custodian | Exact run/container identities, lifecycle operations, private fixture administration, curated build-input export and evidence custody | Must not use its authority to coach an answer into a run or silently repair a failed first result |
| `desk` application container | Builder-authored application image; its own durable checkpoint/artifact volume; authorized business-action credentials and approved provider credentials | Host home/repository/recall, authoring history, Docker socket/API, fixture volume, hidden schedules, expected labels and evaluator storage |
| `fixture` container | Authoritative business services, scoped PostgreSQL access for state/journal/grants/scheduling, and trusted service-event collection | No need for provider credentials, natural-language plan generation, product recovery orchestration or evaluator answer labels |
| PostgreSQL service (instance enrollment pending) | Durable fixture-owned run state and history, accessible to the fixture and authorized custodian/export processes | No direct product-agent SQL access; no fixture credentials in model text; no unrelated workbench data in HEB-154 evidence |
| `provider-egress` relay | Frozen allowlist of provider destinations; transport diagnostics limited by content policy | No fixture administration, world/evaluator volumes, request rewriting, provider adaptation, prompt construction or automatic application-request replay |
| Offline evaluator container | Read-only, immutable evidence export plus separately held expectations; separate writable result directory | No mutation path to the first run, no application/fixture credentials, no default network access |

The fixture may contain the business service and its private scheduler/collector as separately identified processes within the same trusted container. They are not independent judges. The offline evaluator checks persistent state and authoritative inputs without importing the service's business-validation implementation as its oracle. Any later model-based semantic evaluation requires its own approved provider/custody binding; the offline deterministic evaluator does not authorize that access.

### Network and filesystem realization

Propose two explicit internal networks: `business` connects only desk and fixture; `provider-link` connects only desk and egress relay. The relay alone also joins an external-egress network. No fixture, desk or admin port is published on the host. No application container joins host networking, receives extra host mounts, or obtains the engine API. Compose supports explicit network membership and externally isolated internal networks; those features alone do not prove the whole allowed/denied path matrix. [Compose networks](https://docs.docker.com/reference/compose-file/networks/)

PostgreSQL selection adds a fixture-to-database connection whose exact network bindings remain pending enrollment. The desk must not gain a database route or credentials by joining a workbench network or by opening general host-gateway access. The existing server's loopback-published SQL port is an observation, not an accepted new public fixture endpoint or a proven container-to-server path. EN-route in §5 accepts a separate internal database bridge as design, not the workbench network or host-gateway route. Bind and verify the route before use; network attachment and shared-server changes still require separate authorization.

Provider egress uses an allowlisted TLS tunnel to selected provider hosts and ports. TLS remains end-to-end between the builder's adapter and provider. The relay must reject unapproved targets, private/loopback/link-local destinations and redirection or name-resolution routes around the allowlist. It does not terminate provider TLS or collect model content. Actual DNS, host-gateway, IPv4/IPv6 and direct-egress denial require controls before live evaluation. Relay software, exact policy, destinations and credential delivery remain freeze bindings, not existing infrastructure.

Use the accepted private administration model: a Unix-domain socket inside the fixture's private filesystem. The host supervisor reaches a fixed administrative client through the engine's exec channel, with an exact container ID and structured input, not a caller-supplied shell command. The public listener exposes no admin route. The desk cannot mount that socket or invoke the engine. This avoids treating a second port on the same reachable listener as an access boundary. Exact administrative commands, socket ownership and hook messages remain to be frozen.

Use non-root users, a read-only application root, explicitly writable per-run volumes/tmpfs, dropped Linux capabilities, `no-new-privileges` and no automatic container restart. Service process death is not repaired by an implicit Compose policy. Pin images by immutable identity and record the effective launch configuration; freeze resource limits with campaign budgets. Inspect the realized mounts and credential readability: declaring a Compose secret does not by itself establish its desired file ownership. [Compose service settings](https://docs.docker.com/reference/compose-file/services/)

Each campaign run gets fresh fixture and application state. Concurrent orders within a case share that case's fixture inventory; they must not accidentally receive separate worlds. A designated restart reuses the same run identity and durable volumes. Only the named application container/process is terminated in application-crash cases; the fixture survives. Cancellation uses the application's cancellation boundary, not an automatic volume cleanup. Any fixture/collector failure outside the declared fault marks the run's affected evidence unavailable and preserves what exists; it is not converted into an agent success or an unrecorded rerun.

## 4. PB-transport — public service and private control

PB-transport is accepted with plain HTTP/JSON for this local proving run. Propose one public business route, `POST /frd/v1/actions`, carrying the parent contract's action envelope. Here public means application-facing within the private container network, not internet-exposed. It is HTTP/JSON between independent processes, not an in-process call disguised as a tool. Exact route/schema bytes remain to be frozen. The protocol is specific to this proving fixture; the built agents' internal generation schemas remain builder-authored.

Use HTTP, not HTTPS, for the fixture action and observation/hook interfaces. Do not add fixture certificates, a trust bundle or certificate-lifecycle work to this run. Tad's rationale is to avoid certificate overhead in the synthetic, local proving environment. Plain HTTP provides neither transport encryption nor cryptographic service authentication; this is a deliberate limitation, not a claim that network separation provides TLS-equivalent protection. The scoped fixture credentials remain in headers and remain distinct from business approval, but are not encrypted in transit.

Keep this choice inside the accepted private, single-host container boundary with no host-published fixture/admin ports. Provider credentials are not fixture credentials; external model-provider connections retain end-to-end TLS through the transport-only relay. Access enforcement must still be verified before execution. Exposing the fixture beyond this local boundary or moving to non-synthetic business data reopens the transport decision; the proving-run choice is not a production or fleet-wide exemption.

- Send an opaque credential through the transport header, not model text or a claimed role field. The fixture maps it to a run/order/action scope. Credential values are neither fixture labels nor approval grants. Omit secrets from evidence; retain a non-secret credential identity for correlation.
- Authorization and schema checks precede mutation admission. Only a valid, identity-matching typed result can establish commitment or fenced non-application. An HTTP status alone cannot establish the fate of a logical operation, especially after another attempt.
- A valid action response uses the closed parent envelope. Malformed or missing responses remain distinguishable from typed business rejection. Exact status/error unions, request limits and error precedence remain the wire-schema pass; no claim that the nine actions already have complete physical schemas.
- No automatic HTTP redirect, SDK retry, proxy replay or failover around fixture mutations. Each physical dispatch is recorded and budgeted; replay follows the accepted journal design. Disabling implicit retries must be verified in the actual client configuration and with a transmission counter.
- Implement reply-loss faults by actually withholding/closing the response at the declared boundary. Do not return a JSON object labelled timeout. Preserve service commitment and application observation as separate facts.
- Use a separate public observation/hook route with only the application's permitted projection and a non-coaching acknowledgement. It cannot list schedules, fetch evaluator results, release stock or request arbitrary admin actions. An application-supplied hook assertion is not independent proof of service commitment or actual provider bytes.

Private admin requests can initialize a fresh run, install the preregistered schedule, operate named hooks and export evidence. They cannot serve as an application recovery shortcut. The supervisor performs named crash/restart operations against the sealed identity. A trusted collector correlates service and application events while preserving their different origins; exact provider/parser instrumentation must still be bound without replacing the builder's adapter, parser or manifests.

#### EN-access — Restrict HEB-154 logins before the broad rules

Accepted design: a narrowly owned block in the existing mounted `pg_hba.conf`, before its broad TCP rules. The intended order is:

1. Preserve the existing local postgres/peer rule.
2. Allow only the exact active run database, fixture login and fixture source address, with the accepted TLS/client-certificate plus SCRAM authentication.
3. Reject every other TCP request by HEB-154 fixture logins, across IPv4/IPv6, encrypted/plaintext and database/physical-replication requests.
4. Preserve the existing workbench TCP rules in their original order and with unchanged authentication requirements.

Use a dedicated `NOLOGIN` marker role, `heb154_fixture_clients`, with no administrative attributes or explicit object grants; every HEB-154 fixture login belongs to it without membership-administration authority. Its direct/indirect membership selects the rejection rules. No workbench role joins it. Startup checks reconcile the complete HEB-154 login inventory against marker membership and exact allow rows, so a missing membership cannot silently escape the deny block. Create runtime roles as `NOLOGIN`; after rule/ACL checks, enable the exact role only for custodian-controlled TCP validation. Withhold the fixture's credential mount and campaign admission until those actual-role tests pass; disable the role and close only its identified sessions on validation failure. A different test identity cannot prove the runtime identity's access.

This shared-configuration amendment is accepted as design, not as permission to edit or reload the server. PostgreSQL uses the first matching HBA rule; a later reject cannot constrain an earlier broad allow. A reload is needed on this server after a separately approved file edit. Parsed file rows alone do not prove what new connections will experience. [PostgreSQL HBA matching and reload](https://www.postgresql.org/docs/17/auth-pg-hba-conf.html)

Do not revoke `PUBLIC` access on existing workbench databases, change existing roles, weaken TLS, alter the server certificate, or introduce a SQL proxy. Those are wider changes than this proposal. Bind the exact generated rule bytes and source addresses before freeze. Stage and test the rule block on a disposable synthetic PostgreSQL test instance first; shared-server application needs a saved preimage, verified mounted bytes, a controlled reload and a custodian-run workbench connection check. If that check fails, disable HEB-154 admission and restore the verified preimage only if no intervening edit exists; otherwise stop for reconciliation. Do not restart the shared server as recovery.

### Transactions and recovery — transaction and finality design accepted; exact bindings pending

The [PostgreSQL persistence-contract draft](postgresql-persistence-contract.md) records all four PG designs as accepted within scope. PG-finality includes pre-admission fencing and the reconciliation operation-kind/semantic-digest additions; PG-export includes the final seal, correlated snapshot and isolated restore. Exact relation/constraint and grant bindings, executable DDL, canonical identity encodings/wire bytes, numeric limits, export commands/versions, restore configuration, content/retention and enrollment remain open. Design acceptance does not authorize execution or prove these mechanisms.

Use the accepted short Read Committed write transactions with PG-transaction's fixed row-lock order and shared run guard; coherent multi-record reads use short Repeatable Read read-only transactions. Recheck current predicates inside each effect transaction, commit effect/result/history together, and keep hooks and other waits outside transactions and checked-out connections. Exact constraints, executable statements/grants and numeric deadlines still require binding before freeze. PostgreSQL's default Read Committed isolation does not make arbitrary multi-statement read/check/write sequences safe. No automatic effect-transaction retry is permitted in this fixture. Retain confirmed rollback as infrastructure-failure evidence; connection loss around commit remains uncertain until the permitted journal path resolves it. Neither condition silently dispatches another effect or grants fresh budget. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html)

The proposed implementation sequence is:

1. Persist admission of the logical operation and physical attempt without a business effect. A replay atomically consumes its single-use permit with admission of its new attempt.
2. Reach the declared pre-commit hook outside an open write transaction. Never hold conflicting database locks while waiting for a barrier that needs another request to progress.
3. In the effect transaction, recheck the attempt's fence and current grant/references; enforce the cross-key active-allocation guard; write the reservation or arrangement together with its terminal journal result and service-event record. No transaction spans both business effects.
4. After commit, deliver or intentionally lose the response as scheduled. Recover pending event export from the committed record; do not rerun the mutation merely because the collector or client missed it.

Finality/replay closure serializes with admission and effect commitment for the same logical operation under the accepted PG-transaction/PG-finality design. Persistently fence every admitted prior attempt covered by the closure and the named original even if it was delayed before admission. Both late admission and late execution must honor that fence, with another check inside the effect transaction. A confirmed closure issues one generation-bound permit; only its single atomic consumption admits a fresh same-effect attempt in the next generation. Repeated delivery creates no second executor, and historical closure does not establish current finality after newer admission. Preserve append-only attempt events and current-state projections. Exact DDL/keys, comparison encodings, error schemas and export snapshot invariants remain to be frozen; no enforcement proof is claimed.
